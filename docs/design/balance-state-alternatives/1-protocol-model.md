# Why the schema has this shape

## The two decisions everything else follows from

**No nested messages, no `oneof`, no `map`, no `optional`.** Every top-level repeated message becomes a ClickHouse table; a nested repeated message or a `oneof` inside a row is either flattened unpredictably or turns one logical row into a join the consumer did not ask for. And the existing sink already demonstrates the `optional` trap: `erc20/balances/clickhouse/README.md` records that optional `contract` is stored as `String`, so absent-native and empty-ERC-20 are the same value in SQL, and `native/balances/README.md` has to tell consumers to separate the two packages by database. This schema refuses to repeat that. Presence is carried two ways, both of which survive the `String` mapping intact: every protocol integer is a decimal `string` where `""` means "not carried" and `"0"` means an observed zero, and every possibly-empty address is paired with an enum (`UnderlyingKind`, `AliasEndpointKind`, `CashSource`, `AliasRelation`) that states what the emptiness means.

**Per-family global-state messages, one shared holder message.** The LENS is protocol-model fidelity, and a generic key/value state table would type `liquidityIndex` (uint128 RAY), `baseSupplyIndex` (uint64 at 1e15), `chi` (uint256 RAY) and `postTotalEther` (wei) identically, losing the scale and the accrual law. Five family tables plus `MakerPotState` cost DDL, not rows: a package that models only Aave leaves the other tables empty. The holder side is the opposite case — Aave scaled balance, cToken shares, Comet principal, stETH shares, 4626 shares and Pot `pie` are all "one integer stored against an address", differing only in kind, sign and scale, which `BasisKind` + `basis_decimals` + `basis_value` express exactly. One table means one place to ask "what does this address hold across every protocol".

## Message-by-message

**`BlockClock`** — exactly one row per delivered block, always, including blocks with no modelled write. This is what satisfies "carry or explicitly consume canonical block number/hash/parent/timestamp, including blocks without relevant state writes". It also converts the sink's `_blocks_` table (documented as "nonempty-output block markers, not a complete clock history") into a complete clock history *for this package*, because this package's output is never empty. `producer_version` carries `Block.ver`; `parameters_digest` binds every row of the block to the exact `map_events` parameters; `emitted_rows` lets an audit detect rows lost between the map and the sink. There is deliberately **no finality field**: a map cannot observe finality or predict an undo, so forks stay the stream's contract (`BlockUndoSignal.last_valid_block` / `last_valid_cursor`, or `final_blocks_only`). The header comment says so explicitly so nobody adds one later.

**`ModelEpoch`** — the "model/runtime epoch and dependency reference" required by the first acceptance item. `model_epoch_id` is a deterministic string (`<family>/<chain_id>/<contract hex>/<epoch_index>`) repeated on every value row, so a consumer never has to guess which formula produced a number. `revision` + `balance_rounding` carry the Aave rounding era directly: aToken revision ≤3 is `ROUNDING_DIRECTION_HALF_UP`, revision ≥4 (v3.5 `TokenMath.getATokenBalance` → `rayMulFloor`) is `ROUNDING_DIRECTION_FLOOR`. `implementation_code_hash`/`proxy_code_hash` are the runtime binding; `activation_block` + `activation_block_hash` + `activation_ordinal` are the verified witness; `EPOCH_STATUS_UNQUALIFIED` exists because the research leaves every activation block open (Aave revision 4/5 on BSC/Ethereum, Compound cDAI delegate at the epoch, Lido V2/V3/V4 enactment).

**`AssetAlias`** — Arc, expressed as a declaration rather than as observations. `base_*` is the authoritative full-precision endpoint, `alias_*` the reduced-precision interface over the same balance, `conversion_divisor` + `conversion_rounding` the exact integer relation, `sub_unit_only_on_base` the fact that amounts below 10⁻⁶ USDC exist only natively. The two `*_transfer_log_emitter` columns exist because Arc's plain native sends emit `Transfer` from the system emitter while `0x3600…0000` logs only ERC-20-interface activity: a consumer that does not know which emitter is which will count one balance twice, which is precisely the failure #12 names.

**`HolderBasis`** — the shared basis. `basis_kind` is the field that keeps a Comet `int104` from ever being read as an unsigned ERC-20 amount, and `BASIS_KIND_SIGNED_PRINCIPAL` is documented as never clamped: `principal > 0 ? presentValueSupply : 0` is the consumer's projection, not an extraction fact, so negative principal survives into the sink with its sign. `holder_index` carries Aave's `additionalData` (the user's last liquidity index) — the only per-holder index any selected family stores for the supply side. `state_contract`/`state_key` are the explicit dependency reference into the family table. `underlying` + `underlying_kind` + `result_decimals` describe the unit the basis converts *into*, so a cETH row (`UNDERLYING_KIND_NATIVE`, empty address) is never confused with a misconfigured ERC-20 row.

**`AaveReserveState`** — exactly the three storage fields `getNormalizedIncome` reads, typed as they are stored: `liquidity_index` and `current_liquidity_rate` (uint128 RAY, one packed slot), `last_update_timestamp` (uint40, a different slot packed with `deficit`/`id`/`liquidationGracePeriodUntil`). `variableBorrowIndex` and `currentVariableBorrowRate` are deliberately absent — variable-debt tokens are a deferred scope, and adding them later is two new field numbers. `getReserveNormalizedIncome` is deliberately not a column: it is a function of these three fields and the *consumer's* selected clock, and a value the map computed at its own block timestamp would be valid only for that block. Conformance models belong to #16.

**`CompoundV2MarketState`** — every input of `exchangeRateStored = (totalCash + totalBorrows − totalReserves) × 1e18 / totalSupply`, plus `initial_exchange_rate_mantissa` for the `totalSupply == 0` branch, plus the accrual inputs (`borrow_index`, `accrual_block_number`, `reserve_factor_mantissa`) and `interest_rate_model` *identity*. `CashSource` + `cash_source_contract` encode that cash is a cross-contract dependency with three different shapes: `CErc20` reads `underlying.balanceOf(cToken)`, `CEther` reads its own native balance, `CDaiDelegate` computes `pot.chi() × pot.pie(cDAI) / RAY` and is therefore **not** `DAI.balanceOf(cDAI)`. The IRM's parameters (base/multiplier/jump/kink, `blocksPerYear = 2102400`) are not here because `exchangeRateStored` does not need them; `exchangeRateCurrent` does, and that is a future `CompoundV2InterestRateModel` message added with a new `Events` field number.

**`CometMarketState`** — the two packed storage slots that matter for balances (`baseSupplyIndex`/`baseBorrowIndex` from one slot; `totalSupplyBase`/`totalBorrowBase`/`lastAccrualTime` from the other), plus the eight per-second rate immutables and the three scale constants. The tracking indices and pause flags are deliberately omitted: rewards and permissions, not balance inputs. The borrow-side immutables *are* carried, because the basis is signed and debt must stay evaluable without a schema change. The immutables live in the same table on a `MODEL_COVERAGE_CONSTANTS_ONLY` row rather than in a sibling table, so a market is one join, not two — justified because every governance rate change is a new implementation and a proxy upgrade, so constants change exactly when an epoch changes.

**`LidoPoolState`** — both observation paths. The storage path carries `total_shares`/`external_shares` (the packed low/high halves of `keccak256("lido.StETH.totalAndExternalShares")`) and the four internal-ether components (`buffered`, `depositedPostReport`, `clValidatorsBalance`, `clPendingBalance`). The log path carries the `TokenRebased` seven-tuple with `VALUE_PROVENANCE_OBSERVED_LOG`, which gives `postTotalEther`/`postTotalShares` — the post-report share rate — directly, so a rebase row is model-complete without a storage read. `contract_version` is carried because the slot set moves between Lido V2/V3/V4 and the old slots are zeroed at migration; that migration is an `INVALIDATION_KIND_LAYOUT_CHANGED` event, not a balance change.

**`MakerPotState`** — `chi`/`rho`/`dsr` with `ACCRUAL_KIND_COMPOUND_PER_SECOND_RPOW_HALF_UP`. This is the one "shared dependency" table, and it earns its place by serving two families: cDAI's `getCashPrior` (#14) and sDAI's `convertToAssets` (#24). `pot.pie(account)` is *not* a column here — it is a mapping keyed by an address, i.e. a `HolderBasis` row with `BASIS_KIND_NORMALIZED_PIE` and `token = Pot`. That reuse is the clearest evidence the shared holder message is the right abstraction.

**`Erc4626VaultState`** — a *binding*, not a copy. `conversion_model` names the exact implementation formula and `dependency_contract`/`dependency_key` point at the state row that formula reads. A conversion-input change therefore emits a row in the dependency's own table (`MakerPotState` for sDAI, `AaveReserveState` for stata) and nothing here. Only `CONVERSION_MODEL_OZ_VIRTUAL_OFFSET` needs the vault's own `totalSupply`/`totalAssets`/`decimalsOffset`, so those columns stay empty for the other two models. `preview_redeem_equals_convert_to_assets` and `max_redeem_limit_aware` exist because EIP-4626 explicitly permits `convertTo*` to be inexact or time-weighted and permits `preview*` to include fees, and because Aave stata's `maxRedeem` returns 0 while the reserve is paused even though `convertToAssets` is non-zero. A consumer that substitutes one for the other silently reports a wrong number; these two booleans make the substitution checkable in SQL.

**`StateInvalidation`** — upgrade and dependency invalidation with the effect spelled out. The rule is: a *recognized-shape* dependency change (`NewMarketInterestRateModel`, a proxy `Upgraded`, `ContractVersionSet`, a Lido slot migration) becomes an invalidation row and stops projection for that key; an *unrecognized* write to a modelled slot fails the block, per AGENTS.md's fail-closed requirement. `INVALIDATION_EFFECT_RETAINED_STATE_INVALID` is the explicit instruction to rebuild from an #7 checkpoint.

# How each acceptance item is met

**Holder basis updates with chain, token/market, holder, type, exact value, unit/scale, epoch and dependency refs.** `HolderBasis` carries `chain_id` (declared by manifest/parameters, never inferred — the block has no chain id), `token`, `holder`, `basis_kind`, `basis_value` (exact decimal), `basis_decimals` + `result_decimals` (unit/scale), `model_epoch_id` (model/runtime epoch), and `state_contract`/`state_key` (dependency reference). Negative principal is preserved by `BASIS_KIND_SIGNED_PRINCIPAL` with a signed decimal string and a comment forbidding clamping; debt is distinguished from an unsigned ERC-20 balance by the kind enum, and this package emits no raw ERC-20 `balanceOf` at all — that stays with `evm.balances.v1`.

**Protocol-specific global state with indices, rates, clocks, totals, constants and cross-contract inputs; observed vs verified-initial vs derived; never label a partial delta complete.** Six family tables with exactly-typed fields; `ValueProvenance` separates `OBSERVED_WRITE` / `OBSERVED_LOG` / `VERIFIED_INITIAL` / `DERIVED` / `IMPLEMENTATION_CONSTANT` / `DECLARED` and a row is homogeneous in provenance; `ModelCoverage` has no value that means "complete" unless every mutable input of the projection was observed at the same ordinal, and the Compound v2 donation case below is the worked example of `MODEL_COVERAGE_PARTIAL`. Cross-contract inputs are explicit: `CashSource` + `cash_source_contract`, `Erc4626VaultState.dependency_contract`.

**Canonical clock carried for every block; finality and undo left to the stream.** `BlockClock`, one row per delivered block, no finality column, header comment naming `BlockUndoSignal` and `final_blocks_only` as the contract.

**Identity and order from transaction/call/log identity and ordinals, with block/system scopes that need no transaction hash; change boundary vs end-of-block stated.** Fields 2–8 of every observation message: `scope` (`TRANSACTION`/`SYSTEM_CALL`/`BLOCK`/`PACKAGE`), `tx_hash` (empty outside transaction scope), `tx_index`, `call_index`, `log_index`, `ordinal`, and `observation` (`CHANGE_BOUNDARY` / `END_OF_BLOCK` / `DECLARATION`). `ordinal` is the single cross-scope ordering key and is documented as trustworthy on producer versions 4 and 5 only.

**One shared index/rate update affecting initialized holders, without synthesizing holder writes or emitting every holder.** `reprices_dependents` on every family state row marks exactly this situation, and the schema has no mechanism to emit a holder row without a holder storage observation. The Comet and Lido examples below each emit zero holder rows while repricing every holder.

**Missing/uninitialized, known zero, unsupported model, invalidated dependency, reverted; upgrade/dependency invalidation; reuse #7.** The header's six-state table maps each to exactly one place: absence, `STATE_KIND_KNOWN_ZERO`, `STATE_KIND_UNSUPPORTED_MODEL`, `STATE_KIND_INVALIDATED_DEPENDENCY`, `STATE_KIND_REVERTED` (reserved, not emitted, because `common/persist` drops reverted frames), `STATE_KIND_VALUE`. There is no all-holders snapshot message, no cold-start message and no checkpoint message: `VALUE_PROVENANCE_VERIFIED_INITIAL` is the same single-holder pinned-CREATE witness `erc20/balances` already uses, and everything else defers to #7.

**Compatibility, versioning, Rust fixtures; no renumbering, no hidden cache, no RPC, no extra erc20/balances map, no db_out, no custom sink.** See `versioning_rules`. The fixtures are real and run. `evm.balances.v1` is not imported or touched. Nothing in this schema requires an RPC call at map time; the values the map cannot read from a block (Comet immutables, epoch bindings, aliases) arrive as `VALUE_PROVENANCE_IMPLEMENTATION_CONSTANT` / `VALUE_PROVENANCE_DECLARED` rows sourced from caller-qualified parameters, and `parameters_digest` binds them. Each new package has one `map_events`; `erc20/balances` gains nothing.

**Native sink mapping and cross-output consumption without promising atomicity or clock completeness from cursor progress.** See `sink_mapping`, and the third bullet of the header's "what a row is not".

| `LidoPoolState` | one per storage change, one per `TokenRebased` | `(chain_id, steth, ordinal)` | storage rows and log rows coexist, separated by `provenance` | ← `HolderBasis.state_contract` |
| `MakerPotState` | one per `drip()` / `file()` | `(chain_id, pot, ordinal)` | as above | ← `Erc4626VaultState.dependency_contract`; ← `CompoundV2MarketState.cash_source_contract`; ← `HolderBasis` rows with `BASIS_KIND_NORMALIZED_PIE` |
| `Erc4626VaultState` | binding rows per epoch; OZ-model vaults also per `totalAssets`/`totalSupply` change | `(chain_id, vault, ordinal)` | as above | → dependency family on `(chain_id, dependency_contract, dependency_key)` |
| `StateInvalidation` | 0..n | `(chain_id, contract, contract_key, ordinal)` | as above | → family state on `(chain_id, contract, contract_key)`; → `ModelEpoch` on `superseded_epoch_id` |

Eleven tables are created in every sink database even when a package fills three. That is DDL cost, not row cost. Running each family package into its own database (as the repo already recommends for native vs ERC-20) is the operational mitigation.

## Consumption rules

**Ordering.** Within a block, across every table, order by `ordinal`, then `sequence` for ties inside one table. Across blocks, order by `_block_number_`. `_version_` is ingestion time, not chain order — never order by it.

**Latest observed value.** Deduplicate history first (`FROM <table> FINAL WHERE NOT _deleted_`), then take the greatest `(_block_number_, ordinal, sequence)` per key. Do **not** filter zeros before selecting the latest row: a `STATE_KIND_KNOWN_ZERO` row is a real observation, and dropping it resurrects an older non-zero value. This is the same trap the existing sink README documents for `evm.balances.v1`.

**Presence.** Treat `value_column = ''` as "not carried by this row", never as zero. A projection query must reject a row whose `coverage = MODEL_COVERAGE_PARTIAL` as a source of truth for the whole model, and instead carry forward each field's own last non-empty observation.

**Repricing without holder rows.** To value a holder at block N: take the holder's latest `HolderBasis` row at or before N, join the latest family state rows for `(state_contract, state_key)` at or before N, join the latest `MODEL_COVERAGE_CONSTANTS_ONLY` row for the same `model_epoch_id`, and evaluate the family getter against the clock the consumer selected — reading `hash`/`timestamp_seconds` from `BlockClock` at N. Refuse to project when the latest `StateInvalidation` for that key is newer than the latest `ModelEpoch` with `EPOCH_STATUS_ACTIVE`.

**Cross-output consumption.** `evm.balance_state.v1` and `evm.balances.v1` are separate schemas in separate databases. The bridge is `AssetAlias` (Arc: `alias_contract` matches the ERC-20 `Balance.contract`, the native side matches `native/balances` rows) and address equality elsewhere. Sum across the two sides of an alias and you have double-counted one balance.

**What the sink does not promise.** `_blocks_` for this package is a complete clock history only because `BlockClock` makes every block non-empty; it is still not an atomic-publication manifest. ClickHouse writes are not multi-table transactions, so a crash can leave a `BlockClock` row whose sibling rows are missing — compare `emitted_rows` against the actual per-block row count across the ten other tables to detect it. A cursor, or a successful bounded run, is not evidence that every intervening block was written.

## Versioning
## Package identity

`evm.balance_state.v1`, file `proto/v1/balance_state.proto`, generated Rust committed at `proto/src/pb/evm.balance_state.v1.rs` via buf + `buf.build/community/neoeinstein-prost:v0.4.0` (`file_descriptor_set=false`), with a module in `proto/src/lib.rs` mirroring the existing `evm::balances::v1` shape. Each balance-state package's `substreams.yaml` lists `files: [balance_state.proto]`, `importPaths: [../../proto/v1]`, and one module `map_events` with `output.type: proto:evm.balance_state.v1.Events`.

## Relationship to `evm.balances.v1`

No import, no shared types, no field reuse, no reinterpretation. `proto/v1/balances.proto` and `proto/src/pb/evm.balances.v1.rs` are byte-identical before and after this change; `erc20/balances` and `native/balances` are not modified and gain no module. A change that would require touching `evm.balances.v1` is out of scope by definition.

## Additive-change rules

1. **New protocol family** → a new top-level message plus the next free field number in `Events` (12, 13, …). Never renumber an existing `Events` field, never reuse a removed one. Adding a family creates one new sink table and changes nothing existing.
2. **New field in an existing message** → the next free number in that message. Semantics must be additive: a consumer that does not know the field sees the default (`''`, `0`, `false`, enum 0), which every reader already treats as "not carried"/"unusable".
3. **Common identity block** → fields 1..13 mean the same thing in every observation message; 14 and 15 are `reserved` so the next common field lands at one number everywhere. Never use 14 or 15 for a family-specific field.
4. **Removing a field** → `reserved <n>; reserved "<name>";` in the same message. Never reuse the number or the name.
5. **Enums are append-only.** New values get the next free number with the enum-name prefix. Never renumber, never repurpose, never remove a value (deprecate it in a comment and `reserved` the number if truly retired). `UNSPECIFIED = 0` stays in every enum and is never emitted.
6. **Changing what a field means is a breaking change.** Add a new field with a new number and mark the change with a new `model_epoch_id` era; do not redefine the old one. A getter that changes rounding or inputs is an epoch change (`ModelEpoch.revision`, `balance_rounding`, `StateInvalidation` with `INVALIDATION_KIND_IMPLEMENTATION_UPGRADED`), not a schema change.
7. **Breaking anything above** means `evm.balance_state.v2` in a new file, published beside v1, with both maintained until consumers migrate. The `v1` sink tables are never mutated in place.
8. **CI gate.** `buf breaking --against '.git#branch=main'` over `proto/` on every PR, plus `protoc` compile and `buf lint`. A renumber or a type change fails the build.

## Rust encode/decode fixtures

Committed under `proto/tests/` (crate `proto`, host-only, excluded from the WASM ingestion path like the existing tools):

- **Round-trip fixtures**, one per family plus the alias and the clock-only block: build the message in Rust, `encode`, `decode`, assert structural equality, and assert the encoded bytes equal a committed hex vector. The committed bytes are the compatibility contract: a change that alters them without a deliberate version bump fails.
- **Invariant fixtures** asserting the rules the type system cannot: `state_kind ∈ {VALUE, KNOWN_ZERO}` implies the family's required value fields are non-empty; `state_kind ∈ {UNSUPPORTED_MODEL, INVALIDATED_DEPENDENCY, REVERTED}` implies every value field is empty; `coverage = MODEL_COMPLETE` implies the family's full mutable input set is non-empty at one ordinal; `coverage = CONSTANTS_ONLY` implies every mutable field is empty; `scope ∈ {BLOCK, SYSTEM_CALL, PACKAGE}` implies `tx_hash` is empty; `basis_kind != SIGNED_PRINCIPAL` implies `basis_value` has no leading `-`; `basis_kind = SIGNED_PRINCIPAL` round-trips a negative decimal unchanged.
- **Forward-compatibility fixtures**: decode a message carrying an unknown enum number and assert it survives as the raw `i32` (verified — prost generates enum fields as `i32`); decode a v1 message with a committed v1.1 field appended and assert the v1 reader ignores it.
- **Golden-decimal fixtures**: `uint256` max, `int104` min and max, `1e27`, `1e15`, and a 78-digit value, all as decimal strings, to prove no numeric field silently narrows.

**Known prost limitation to write into the test doc:** prost does not retain unknown fields, so decoding a v1.1 message with v1-generated types and re-encoding it *drops* the newer fields. Sinks decode and write; they must never round-trip a message through an older generated version. The fixtures assert the decode direction only.

## Risks
- Enum-to-SQL representation is unverified. The native CLI may render enums as an integer, as the value name, or as Enum8, and live sink use is paused, so no generated schema could be inspected. Enum *numbers* are the stable contract; verify the generated DDL on the first authorized sink run before writing any query that filters on an enum name.
- bytes maps to String, so an empty address and an absent one are identical in SQL. Every possibly-empty address is paired with an enum (UnderlyingKind, AliasEndpointKind, CashSource, AliasRelation) to make the emptiness self-describing, but a consumer that reads the address column alone can still misread it. This is the same class of defect the existing optional `contract` column has.
- The empty-string-means-not-carried convention cannot be enforced by the type system. A package bug that writes "" where it meant "0" is indistinguishable from "not carried" unless state_kind and coverage are cross-checked. The invariant fixtures listed in versioning_rules are the only guard, and they run offline against constructed messages, not against real producer output.
- Eleven tables are created in every sink database even for a package that fills three. Separate per-family databases are the operational mitigation; the schema itself cannot avoid it while keeping per-family typed fidelity.
- Every storage-layout fact behind these messages is inferred from source declaration order, not from a compiler storage-layout dump: Aave ReserveData slot offsets, Comet CometStorage slot indices behind the transparent proxy, the legacy 2019 cUSDC runtime layout, and the Lido `shares` mapping (expected slot 0). This schema types the values; it does not qualify the reads. Those remain open questions 6-9 of docs/extraction-coverage.md.
- No epoch activation block is known. Aave aToken revision 4/5 activation on BSC and Ethereum, the cDAI delegate and interest-rate model in force at the chosen epoch, which Comet proxies run legacy Comet versus CometWithExtendedAssetList, and Lido V2/V3/V4 enactment blocks all have to be read from chain before ModelEpoch.activation_block can be filled. EPOCH_STATUS_UNQUALIFIED exists for that gap and must be the default until each is bound.
- prost retains no unknown fields, so decoding a future message with v1-generated types and re-encoding it silently drops the newer fields. Sinks must decode and write, never round-trip through an older generated version. Unknown enum numbers are safe (verified: enum fields generate as i32).
- BlockClock makes every block nonempty, which gives this package a complete clock history in the sink, but ClickHouse writes are still not multi-table transactions: a crash can leave a BlockClock row whose sibling rows are missing. emitted_rows makes that detectable after the fact; it does not prevent it, and no schema field can.
- Comet rate immutables are baked into each implementation and re-deployed on every governance rate change. A production map cannot call a getter, so they arrive as caller-declared IMPLEMENTATION_CONSTANT rows. An upgrade that is not caught as INVALIDATION_KIND_IMPLEMENTATION_UPGRADED leaves stale constants in the sink with no signal, so proxy-upgrade detection is load-bearing rather than optional.
- Compound v2 cDAI's CashSource may be wrong for the chosen epoch: the pinned records show a DSR-integrated CDaiDelegate, but CErc20Delegator implementations are governance-upgradeable and the live implementation was not read. Until it is, the MAKER_POT cash path is an assumption the schema faithfully encodes rather than a verified fact.
- Lido reports are not guaranteed to emit exactly one TokenRebased, so a consumer keying rebases on that log alone may miss a report. The storage-component columns exist for that reason, but their slots move between contract versions and the `shares` slot index is itself unverified.
- Arc facts are thin: chain id, finality tag semantics, fee recipient, and whether the system emitter also logs debits are open questions. The AssetAlias row is a caller declaration with VALUE_PROVENANCE_DECLARED and is only as good as the qualification behind the parameters that produced it.
- Thirteen denormalized identity columns on nine tables widen every row; the String model_epoch_id repeated on each row is the largest per-row cost. ClickHouse compresses it well and a LowCardinality or dictionary mapping is a sink-side optimization, but a very high-cardinality holder workload should measure it before committing.
- Deferred scopes are absent by design and their absence must not be read as support: no Aave variable debt, no Compound v2 borrow snapshots, no Comet collateral positions, no wstETH conversion, no withdrawal-queue NFTs, no Venus ERC-4626 (no per-vault address is confirmed in any official source). Each is new messages or new field numbers later, never a reinterpretation of an existing field.
