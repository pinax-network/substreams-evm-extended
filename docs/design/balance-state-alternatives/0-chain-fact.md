WHY EACH MESSAGE EXISTS

`Events` — one map output per block, six top-level repeated fields, hence exactly six sink tables. The split is by *fact kind*, not by protocol: adding Lido or ERC-4626 adds enum values and rows, never a table. No nested repeated field and no oneof anywhere, so no consumer pays a JSON/Nested/Map column.

`BlockClock` (one row per delivered block, always) — carries chain_id, number, hash, parent_hash, timestamp, state_root. The Extended block has no chain id, so chain_id is a caller parameter echoed for audit; the manifest binds the network (same rule as native/balances). Emitting it on every block, including blocks with no protocol activity, is what makes the clock consumable: Aave's `calculateLinearInterest`, Comet's `getNowInternal() - lastAccrualTime`, sDAI's `rpow(dsr, now - rho)` and Compound v2's `block.number - accrualBlockNumber` all need a canonical (number, timestamp) for heights where nothing was written. It also makes `_blocks_` in the native sink a complete delivered-block list for this package instead of a nonempty-output list. `producer_version` records `Block.ver` (only 4/5 are acceptable; version 3 has the cross-scope ordinal problem documented in the persisted-effect matrix). `spec_revision`, `package`, `package_version` are provenance for the emitting artifact. The five `*_count` fields exist because ClickHouse writes are not multi-table transactions: a consumer can verify every row of a block landed without trusting the cursor.

`EpochEvent` — the model/runtime binding, which is exactly the thing a balance number is meaningless without. One row states family, `model_id` (the exact formula), `source_pin` (repo@commit the model follows), `implementation_revision` (ATOKEN_REVISION 5, Lido contract version 4), the basis kind/scale/rounding, the basis bit range and signedness, the market and implementation code hashes and the pointer slot, the activation (block, ordinal), and the denominated asset and its decimals. `BOUND` at activation, `REAFFIRMED` on a heartbeat so a consumer that starts mid-epoch can recover the binding from the stream (this restates *model metadata only* — never a holder balance — so it is not a competing bootstrap for #7), `INVALIDATED` at a verified on-chain trigger with the evidence cited, `SUSPENDED` for a declared unqualified era. `basis_carryover` / `global_carryover` answer the question every upgrade raises: Aave revision 4 -> 5 changes rounding but not the holder word (carryover true), Lido v2 -> v3 keeps `shares` but moves totalShares to a new packed slot and zeroes the old one (basis carryover true, global carryover false), a Comet implementation swap replaces the rate immutables (global carryover false).

`Dependency` — the graph the lens asks for, as rows rather than prose: `role` (IMPLEMENTATION, BEACON, PROXY_ADMIN, POOL, UNDERLYING, INTEREST_RATE_MODEL, RATE_ACCUMULATOR, ACCOUNTING, WRAPPED_ASSET), `parent` + `depth` so token -> pool -> rate model -> underlying is walkable, and `binding` + `code_hash` / `pointer_contract` + `pointer_slot` + `pointer_value` so each edge says how it is checked and therefore what invalidates it.

`Alias` — Arc's one balance at two precisions. It is a declaration, not a balance: the ERC-20 view is computed from the primary side's rows by `floor(native * asset_scale / alias_of_scale)`. No second asset, no synthesized holder rows.

`HolderBasis` and `GlobalState` — the two fact tables, deliberately parallel (same provenance block, same observation/boundary/scope/ordinal block) so one audit query shape works on both, and deliberately separate because they have different keys and wildly different cardinalities: holder rows are per (market, holder), global rows are per (market, field, key). Both carry `storage_contract` + `storage_slot` + `raw_previous_word` + `raw_word` + `bit_offset` + `bit_width` + `signed`, so a row can be re-derived from the raw persisted word by an auditor with no access to the mapper.

WHY THE DESIGN AVOIDS `optional`

`evm.balances.v1.Balance.contract` is `optional bytes`, and the native sink stores it as `String`, so absent-native and empty-ERC-20 are indistinguishable in SQL (documented in erc20/balances/clickhouse/README.md and native/balances/README.md). This schema uses no `optional` at all: empty bytes means absent and the meaning is disambiguated by a sibling enum (`scope` says whether `transaction_hash` should exist; `basis_kind`/`family` say whether `market` is a native asset). Proto and SQL then agree, and the existing lossy-presence footgun is not reproduced.

HOW EACH ACCEPTANCE ITEM IS MET

1. Holder basis updates. `HolderBasis` carries chain (`chain_id`), token/market (`market`), holder, type (`basis_kind` = RAW_UNSIGNED / SCALED / SHARES / SIGNED_PRINCIPAL), exact integer (`value` as a decimal string, `previous_value` for the pre-block word), unit/scale (`scale` plus `EpochEvent.balance_asset`/`balance_decimals`/`basis_scale`/`balance_rounding`), model and runtime epoch (`epoch` -> EpochEvent with model_id, source_pin, implementation_revision, code hashes) and dependency references (`epoch` -> Dependency rows). Negative principal is preserved because values are strings and `BASIS_KIND_SIGNED_PRINCIPAL` + `signed` + `bit_width = 104` state the two's-complement decode; the enum documents that negative principal is debt, that `balanceOf` is 0 for it, and that `borrowBalanceOf` uses the borrow index with ceil rounding — so a debt row can never be mistaken for an unsigned ERC-20 balance, which is `BASIS_KIND_RAW_UNSIGNED` with `scale = "1"`.

2. Protocol-specific global state. `StateField` names stored indices (AAVE_LIQUIDITY_INDEX, COMET_BASE_SUPPLY_INDEX/BORROW_INDEX, COMPOUND_V2_BORROW_INDEX, MAKER_POT_CHI), rates (AAVE_CURRENT_LIQUIDITY_RATE, COMET_*_RATE_*, COMPOUND_V2_IRM_*, MAKER_POT_DSR), accrual clocks (AAVE_LAST_UPDATE_TIMESTAMP, COMET_LAST_ACCRUAL_TIME, COMPOUND_V2_ACCRUAL_BLOCK_NUMBER, MAKER_POT_RHO), required totals and constants (COMPOUND_V2_TOTAL_SUPPLY/BORROWS/RESERVES/INITIAL_EXCHANGE_RATE_MANTISSA/RESERVE_FACTOR_MANTISSA, COMET_TOTAL_SUPPLY_BASE/TOTAL_BORROW_BASE/BASE_SCALE/BASE_INDEX_SCALE/FACTOR_SCALE, LIDO_TOTAL_SHARES/EXTERNAL_SHARES, ERC4626_TOTAL_SUPPLY/TOTAL_ASSETS/DECIMALS_OFFSET) and cross-contract inputs (COMPOUND_V2_TOTAL_CASH read from the underlying's storage; MAKER_POT_* read from MCD_POT; AAVE_* read from the Pool for a vault market). `Observation` separates OBSERVED_DELTA from VERIFIED_SNAPSHOT (constants, code immutables, deployment invariants, echoed parameters) from DERIVED (pure function of same-block rows only). A partial delta can never be labelled a complete snapshot because a row describes exactly one field of one slot and `Boundary` states whether it is a change boundary or the end-of-block value; the only "complete" statement in the schema is per-field, and `LIDO_TOTAL_POOLED_ETHER` is explicitly DERIVED-only and only when every component appeared in the same block.

3. Canonical clock and finality. `BlockClock` is emitted for every delivered block, with hash, parent_hash, timestamp and state_root, including blocks with no relevant state writes. The file header states that rows carry no finality and that forks arrive as `BlockUndoSignal` with `last_valid_block`: every row above it must be discarded, and `final_blocks_only` suppresses undo signals. A map cannot see the future, so no field claims finality or predicts undo.

4. Identity and ordering. Every fact row carries `ordinal` (and `first_ordinal` for the reduced range), `transaction_index`, `transaction_hash`, `call_index`, plus `ChangeScope` = TRANSACTION / SYSTEM_CALL / BLOCK / EPOCH / DERIVATION. Block, system, epoch and derivation scopes have an empty `transaction_hash` by construction, so no consumer needs a transaction hash it cannot have. `Boundary` states, per row, whether it is a change boundary (BOUNDARY_CHANGE, opt-in) or the end-of-block state (BOUNDARY_END_OF_BLOCK, always emitted). Ordering within a block is by execution ordinal across all scopes (only producer versions 4/5, per the persisted-effect matrix); each message documents a total sort key so `_row_id_` is deterministic across replays.

5. One shared update, many holders. Documented on `HolderBasis`: a row is emitted only when the holder's basis word was written. A shared index/rate update emits `GlobalState` rows and zero holder rows; consumers retain the last basis per (market, holder) and the last global per (market, field, key) and evaluate at a selected canonical block using that block's `BlockClock`. No holder storage write is synthesized and no holder is re-emitted on an unrelated block. This is the Comet and Lido case below.

6. The five distinguishable states. *missing/uninitialized* = no row since the consumer's checkpoint (absence is never zero; #7 owns initialization). *known zero* = a row with `value = "0"`. *unsupported model* = `EPOCH_EVENT_KIND_SUSPENDED` (declared) or a module error that fails the whole block (live, for a write the bound layout does not describe) — never a silent gap. *invalidated dependency* = `EPOCH_EVENT_KIND_INVALIDATED` with a DEPENDENCY_* / RATE_MODEL_CHANGE / STORAGE_MIGRATION reason and cited evidence, plus `basis_carryover`/`global_carryover` on the next BOUND row telling the consumer precisely which retained state survives. *reverted* = never emitted at all: reverted frames and failed transactions produce no rows under the shared `common/persist` rules, and attempted-but-not-persisted execution belongs to #18. Upgrade/dependency invalidation is defined by `InvalidationReason` (pointer write, code change, dependency code change, dependency pointer write, rate model change, contract version set, storage migration, unsupported write, parameter rebind, unqualified era). Checkpoints, holder coverage and rollback are explicitly delegated to #7 in the file header; the REAFFIRMED heartbeat restates model metadata only and initializes nothing.

7. Compatibility and fixtures. See versioning_rules. No field of `evm.balances.v1` is renumbered, retyped or reinterpreted; nothing is added to it; `erc20/balances` gains no module. There is no hidden cache (the only state is the block being mapped), no RPC in production, no `db_out` and no custom sink.

8. Sink mapping and cross-output consumption. See sink_mapping. Atomicity is explicitly not promised: per-block row counts plus `_blocks_` markers are offered as *checks*, and the text states that sink cursor progress alone is not a complete-clock or publication guarantee.

## Sink mapping
NATIVE SINK MODEL (Substreams CLI native ClickHouse sink, no db_out, no custom sink, no schema override)

The CLI derives one table per top-level repeated message of the output and adds the same five system columns observed in the captured evidence at erc20/balances/clickhouse/evidence/schema.json: `_block_number_` UInt64, `_block_timestamp_` DateTime, `_version_` Int64, `_deleted_` Bool, `_row_id_` UInt32; engine ReplacingMergeTree(_version_, _deleted_), PARTITION BY toYYYYMM(_block_timestamp_), PRIMARY KEY _block_number_, ORDER BY (_block_number_, _row_id_). The scalar-free `Events` wrapper does not become a table. A `_blocks_` table (number, hash, timestamp, version, deleted) holds block markers.

TABLES (six, one per top-level repeated field)

1) BlockClock  <- Events.blocks         — exactly 1 row per delivered block, `_row_id_` = 0.
2) EpochEvent  <- Events.epoch_events   — 0..n; only at activations, heartbeats, invalidations, suspensions.
3) Dependency  <- Events.dependencies   — 0..n; emitted with BOUND/REAFFIRMED rows only.
4) Alias       <- Events.aliases        — 0..n; BOUND/REAFFIRMED cadence only.
5) HolderBasis <- Events.holder_bases   — 0..n; only holders whose basis word was written.
6) GlobalState <- Events.global_states  — 0..n; one row per decoded field per written slot per consuming market.

COLUMN TYPES (derived from the captured native mapping; run `make setup` and diff the generated DDL before trusting any row of this table in production — live sink use is paused)

| proto type            | ClickHouse column | notes |
| --------------------- | ----------------- | ----- |
| string                | String            | exact decimal integers (`value`, `previous_value`, `scale`, `basis_scale`) and identifiers (`model_id`, `source_pin`, `package`) |
| bytes                 | String            | hex under `--bytes-encoding 0xhex` (addresses, hashes, 32-byte slots, raw words). "" means absent; there is no NULL |
| uint64                | UInt64            | `number`, `timestamp`, `ordinal`, `first_ordinal`, `activation_block`, `chain_id` |
| uint32                | UInt32            | `epoch`, `transaction_index`, `call_index`, `change_count`, `bit_offset`, `bit_width`, `depth`, counts |
| bool                  | Bool              | `signed`, `basis_signed`, `basis_carryover`, `global_carryover` |
| enum                  | UNVERIFIED        | lands either as the numeric value (Int32) or the value name (String) depending on CLI version; must be confirmed in a bounded smoke run before any SQL predicate is written against it (see risks) |

No column is a float. No column is Nested/Array/Map/Tuple, because no row contains a repeated field, a nested message or a oneof.

ROW KEYS, DETERMINISM AND DEDUPE

`_row_id_` is the element index, so identical replays must produce byte-identical ordering. Each message therefore declares a total sort key and the mapper sorts before emitting:
- BlockClock: single row.
- EpochEvent: (market, epoch, ordinal, kind).
- Dependency: (market, epoch, depth, role, contract).
- Alias: (asset, alias_of).
- HolderBasis: (market, holder, ordinal, boundary).
- GlobalState: (market, field, key, ordinal, boundary).

Natural (logical) keys, which are what a consumer should join and deduplicate on rather than `_row_id_`:
- BlockClock: (chain_id, number).
- EpochEvent: (chain_id, market, epoch, kind, _block_number_, ordinal).
- Dependency: (chain_id, market, epoch, role, contract, _block_number_).
- Alias: (chain_id, asset, alias_of, _block_number_).
- HolderBasis: (chain_id, market, holder, _block_number_, ordinal, boundary).
- GlobalState: (chain_id, market, field, key, _block_number_, ordinal, boundary).

Replay dedupe: a deterministic replay writes the same (_block_number_, _row_id_) with a newer `_version_`, so `FINAL` collapses it, exactly as the captured 14-physical/7-deduplicated smoke result showed. `_version_` is ingestion time, not chain order: never use it to order chain history; order by (`_block_number_`, `ordinal`).

Shared-write dedupe: when several configured markets consume the same persisted write (Maker `Pot.chi` read by both sDAI and cDAI; one Aave reserve write read by an aToken market and a stata vault), one GlobalState row is emitted per market. The single underlying chain fact is identified by (storage_contract, storage_slot, bit_offset, _block_number_, ordinal) — deduplicate on that tuple when counting facts, and keep the per-market rows when evaluating balances.

JOIN IDENTITIES

- Evaluation join: HolderBasis (market, holder, epoch) x GlobalState (market, field, key, epoch) x EpochEvent (market, epoch) x BlockClock (number), with "last row at or before the selected block" semantics on each side. The epoch column is the guard: a holder basis from epoch 1 must not be evaluated with epoch 2's formula unless epoch 2's BOUND row has basis_carryover = true.
- Cross-output join to `evm.balances.v1`: (block number, market/contract, holder/address). erc20/balances and native/balances rows carry no block hash and store `contract` as String with no absent/empty distinction, so join them by package-separated databases (the existing README rule) and use this package's BlockClock.hash/parent_hash to bind a height to a canonical chain. Within one database, BlockClock is the only in-band chain-identity anchor; treat a BlockClock row whose parent_hash does not match the previous block's hash as a reorg boundary, not as data.
- Cross-output join to #18/#19/#20 execution facts: (block number, transaction_index, transaction_hash, call_index, ordinal). Rows in BLOCK / SYSTEM_CALL / EPOCH / DERIVATION scope have an empty transaction_hash on purpose and must be joined by (block number, scope, ordinal) instead.

COMPLETENESS, NOT ATOMICITY

ClickHouse writes here are not multi-table transactions, and a cursor or a successful bounded run is not a per-block publication manifest (the captured smoke run stored a cursor for 122288010 while stopping at 122288020). Two in-band checks are offered and neither is a guarantee:
1. `_blocks_` lists blocks with nonempty output; because BlockClock is emitted for every delivered block, for this package that becomes a complete list of delivered blocks between the first and last ingested height — gaps in `number` are then real gaps, not empty blocks.
2. BlockClock's five `*_count` columns state how many rows of each table belong to the block, so a consumer can verify, per block, that every row landed:
   SELECT b.number FROM BlockClock FINAL b
   LEFT JOIN (SELECT _block_number_ n, count() c FROM HolderBasis FINAL GROUP BY n) h ON h.n = b.number
   WHERE b.holder_basis_count <> ifNull(h.c, 0);
Anything beyond that (finality, reorg completeness, holder coverage) is outside this schema and belongs to the stream contract and to #7.

OPERATIONAL RULES (inherited from the existing sink README)
- One database per package and per parameter set. Changing package, parameters, chain, bytes encoding, or turning on BOUNDARY_CHANGE rows changes row identity and requires a fresh database and state directory.
- Keep zero-valued rows. Filtering `value = '0'` before selecting the latest row per key resurrects an older nonzero value and destroys the known-zero/missing distinction.
- Parse `value` as Int256 (not UInt256) whenever basis_kind is SIGNED_PRINCIPAL; every other row is non-negative.

NAMESPACE AND THE UNTOUCHED CANONICAL SCHEMA
- New file `proto/v1/balance_state.proto`, new package `evm.balance_state.v1`, generated into `proto/src/pb/evm.balance_state.v1.rs` alongside the existing `evm.balances.v1.rs`. `proto/v1/balances.proto` is not edited: no field renumbered, no wire type changed, no field added, no comment reinterpreted, and its committed SHA-256 (1d8dd199cda6185d4a159abbc4e9afc404d8e698d7428266ea559b2d8d24ec6a, recorded in docs/migration.md) must stay identical. `erc20/balances` keeps exactly one `map_events` and its existing output type.
- Balance-state packages are new workspace members (aave/balance-state, compound-v2/balance-state, compound-v3/balance-state, later lido/balance-state, erc4626/balance-state, arc/balance-state), each with one RPC-free `map_events` over `sf.ethereum.type.v2.Block` emitting `evm.balance_state.v1.Events`. No `db_out`, no database-change module, no custom sink, no imported map dependency, no map cache, no RPC on the production path.

CODE GENERATION
- buf with the neoeinstein-prost plugin, proto3, generated Rust committed under `proto/src/pb/`, `proto/src/pb/mod.rs` gaining a `balance_state::v1` module next to `balances::v1`. Generation must be byte-stable: regenerating on the pinned toolchain produces an identical file, and its SHA-256 is recorded next to the existing artifact hashes in docs/migration.md. Host tooling stays out of the WASM ingestion path.
- Verified offline in this design pass with prost-build 0.13.5 + protoc 34.1 (the workspace prost line), which is the same descriptor the neoeinstein-prost plugin consumes; the buf remote plugin itself was not contacted (network use stays paused).

WITHIN v1 (additive only)
- Field numbers are append-only and never reused, never retyped, never re-meant. A removed field becomes `reserved <n>;` plus `reserved "<name>";`. Note the deliberate numbering gap in `EpochEvent`: fields 32-35 were appended after 21-31 already existed; appending out of visual order is correct and renumbering to tidy it is forbidden.
- Enums are open in proto3 and every one starts at `*_UNSPECIFIED = 0`. New values are appended; existing numbers never change meaning. `StateField` reserves a numeric block per family (Aave 1-9, Compound v2 10-29, Comet 30-59, Lido 60-69, Maker Pot 70-79, ERC-4626 80-89); a new family takes the next free block of ten, a new field of an existing family takes the next free number inside its block.
- A consumer that receives an unknown enum value has an *unsupported model* for that row: it must fail closed for that row (and for any evaluation depending on it) and must never treat it as UNSPECIFIED or guess a default. `*_UNSPECIFIED` itself is never a valid input to an evaluation; producing it is a producer bug.
- `BlockClock.spec_revision` versions the emission RULES, which change more often than the wire format: a new StateField, a new Observation usage, a changed sort key, a new fail-closed condition. It starts at 1. A consumer records the maximum revision it has been qualified against; on a higher revision it must stop and be re-qualified rather than assume the extra rows are ignorable. `package` and `package_version` identify the emitting artifact so evidence can be bound to a specific SPKG digest.
- Adding a new top-level repeated field to `Events` adds a new sink table and is a spec_revision bump plus a fresh sink database; it is not a wire break.

BREAKING CHANGES
- Renumbering, retyping, reinterpreting an existing field, or changing a row's natural key requires `evm.balance_state.v2` in a new file and a new package. v1 and v2 packages can run side by side into separate databases during a migration; a single package never emits both.
- The unit/scale of a field is part of its meaning: changing a `scale` convention (e.g. emitting an index already divided) is a v2 change, not a spec_revision bump.

RUST ENCODE/DECODE FIXTURES (the committed conformance surface)
Fixtures live with the proto crate and run in the offline workspace test job (`cargo test --locked`), with no network and no RPC:
1. Per-family golden `Events` messages — Aave supply, Comet accrual-without-holder-change, Compound v2 donation-only cash, Lido rebase, ERC-4626 conversion-input change, Arc alias declaration, and a clock-only block — each encoded to a committed `.bin` whose SHA-256 is asserted, then decoded and compared field by field. This pins the wire bytes, so an accidental renumbering fails the test rather than silently reinterpreting history.
2. Round trip on every message including empty-bytes-vs-absent: encode, decode, assert equality, and assert that an empty `market`/`transaction_hash`/`alias_of` survives as empty (the schema uses no `optional`, so presence is never consulted).
3. Signed values: `BASIS_KIND_SIGNED_PRINCIPAL` with a negative `value` ("-250000000") round-trips as a string and parses to the same Int256; a uint256-max value ("115792089237316195423570985008687907853269984665640564039457584007913129639935") round-trips.
4. Forward compatibility: a message carrying an unknown enum number (e.g. `field = 9999`) and an unknown field number decodes without loss and re-encodes identically, proving the open-enum and unknown-field rules a consumer depends on.
5. Determinism: a fixed set of unsorted inputs produces one canonical ordering per table (the documented sort keys), asserted twice to catch map-iteration nondeterminism, because `_row_id_` is the element index.
6. Compatibility guard: a test decodes the v1 golden bytes with the current generated types and asserts every field lands where it did, so any future edit to the proto that is not purely additive fails CI.
7. Cross-schema guard: a test asserts `evm.balances.v1` golden bytes still decode with the committed generated types, so balance-state work cannot regress the canonical schema.
Items 2, 3 and 4 were already executed in this design pass against the generated Rust and passed; the golden `.bin` files and the remaining items are implementation work for the first balance-state package.

## Risks
- Enum-to-ClickHouse column type is unverified. The captured schema evidence (erc20/balances/clickhouse/evidence/schema.json) contains no enum field, so whether the native sink writes enums as Int32 or as their value name is unknown. Every SQL predicate on `field`, `observation`, `boundary`, `scope`, `basis_kind`, `reason` or `role` depends on it. It must be settled by a bounded smoke run against the generated DDL before any dashboard or audit query is written — and live sink use is currently paused, so this cannot be closed offline.
- Six tables per package, multiplied by the number of balance-state packages, against the existing operational rule that packages must not share a database (contract='' ambiguity). Operators get a much larger surface to keep separated and to migrate on every schema change. A mis-shared database silently mixes markets from different chains, since `chain_id` is a caller parameter and not enforced by the sink.
- Every layout claim is only as strong as its qualification, and the key ones are still open questions in docs/extraction-coverage.md: the Aave `_userState` and `ReserveData` slot offsets (inferred from declaration order, never confirmed against a compiler layout dump), the Comet storage slots behind the transparent proxy, the legacy 2019 cUSDC storage layout, the USDC `balances` mapping base used in the donation example, and the exact bit split of Lido's packed CL and buffered-ether slots. The schema makes those claims auditable (every row cites slot, raw words and bit range) but does not make them true; a wrong `bit_offset` produces confidently wrong integers.
- One persisted write consumed by several configured markets produces one row per market (Pot.chi for sDAI and cDAI; one Aave reserve write for the aToken market and the stata vault). This inflates GlobalState and means a naive `count()` over-counts chain facts. The documented dedupe key (storage_contract, storage_slot, bit_offset, block, ordinal) fixes the count but must actually be used.
- Emitting a BlockClock row on every delivered block removes the empty-block optimization: the sink writes on every block for every balance-state package, and `_blocks_` grows with chain height rather than with activity. That is the deliberate price of a usable clock for time-dependent evaluation, but it is a real ingestion-volume and storage change relative to erc20/balances.
- The DERIVED row (LIDO_TOTAL_POOLED_ETHER) creates two paths to the same number: the map's in-block derivation and the consumer's own derivation from retained state. They can disagree if the consumer implements the formula differently, and the map can only derive on blocks where every input happened to be written. Mitigation is that the derivation is pinned by `model_id` and must be reproduced by the #16 Rust conformance model, but a consumer that trusts the DERIVED row on report blocks and derives on other blocks may see a discontinuity caused by its own code.
- `value` is a String in both proto and SQL, so nothing mechanically prevents a consumer from parsing a negative `BASIS_KIND_SIGNED_PRINCIPAL` row into an unsigned type. The failure is a parse error at best and a wrapped huge positive balance at worst. Only the documented rule and the `basis_kind` guard stand between a Comet debt row and a fabricated supply balance.
- Packed-slot decoding emits rows where `value == previous_value` (an external-shares row on a totalShares write, a pauseFlags-adjacent field). These are observed confirmations, not changes; a consumer counting rows as changes, or triggering re-evaluation per row, will over-trigger. The distinction is only in comparing two columns.
- The REAFFIRMED heartbeat could be misread as a bootstrap mechanism competing with #7. It restates model metadata only and never a holder balance, but an operator who sees periodic full bindings in the stream may wrongly conclude that holder coverage is also being re-established. The heartbeat interval also sets a hard floor on recovery latency for a consumer that starts mid-epoch: before the first heartbeat it has *missing* model parameters and must not evaluate.
- Turning on BOUNDARY_CHANGE (intermediate) rows changes both row volume and `_row_id_` assignment for every table, so it is effectively a different schema instance that needs a fresh database. If enabled by mistake mid-stream, the sink will interleave two row-identity regimes in one table and `FINAL` will not detect it.
- Fail-closed on an undescribed write stops the whole block for every market in the package, not just the offending one. That is the correct and consistent choice (it matches erc20/balances and native/balances), but in a multi-market package one unqualified upgrade halts every other market's ingestion until parameters are updated — an availability cost that grows with the number of markets per package.
- Compound v2 cDAI is only expressible if the implementation in force at the epoch is known: with the DSR delegate active, totalCash is Pot.chi*pie/RAY, while a plain CErc20Delegate makes it DAI.balanceOf(cDAI). The dependency set and therefore the rows differ completely, and which applies cannot be determined offline (open question in the Compound research). Binding the wrong one produces a plausible but wrong exchange rate.
- Extended blocks expose storage that was written, never storage that was merely read. Any global input that exists but is not written in the observed range is invisible to the map, so `VERIFIED_SNAPSHOT` rows and #7 checkpoints carry real epistemic weight: a consumer that starts cold and sees no AAVE_LIQUIDITY_INDEX row for a quiet reserve has *missing*, not a stale-but-usable value, and must not evaluate. No field in this schema can repair that; it is a property of the source.
